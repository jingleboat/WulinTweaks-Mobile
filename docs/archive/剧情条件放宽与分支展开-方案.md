# 剧情条件放宽 / 剧情分支展开 —— 机制现状与改造方案

> 讨论稿 · 2026-11-03
> 适用：大侠立志传（WulinSH）双端 mod —— PC（BepInEx + Harmony，v1.11.54）与 Android（原生 hook，v163）
> 本文只讨论**逻辑与规则**，不含具体代码；所有数据均来自离线资产分析与实机日志。

---

## 一、两个功能是什么

| 功能 | 一句话 | 作用层 |
|---|---|---|
| **剧情条件放宽** | 把「某角色在队」这类条件从判定里**丢掉**，让剧情在该角色不在队时也能触发 | 条件层（`ConditionNode.CheckAllConnectNode`） |
| **剧情分支展开** | 把一对互补门（在队 / 不在队）由 **if-else 改写成顺序播放**：先播在队侧内容，再播不在队侧内容 | 门层（`HoldNode.CheckCondition`）+ 连线 |

两者独立开关、独立名单，但都作用在同一批「需要伙伴」类型的条件上，因此会互相影响。

### 分支展开的判定（形式化）

```
门对 P = (G0, G1)：父节点某出口恰好 2 条连线，两个条件的 partnerID 相同、Negate 互补
region(P) = Reach(First) − Reach(Second) − {First, Second}
            First/Second = 父端口连线的第 1 / 第 2 条（引擎按顺序问，第一个满足的就被走）
exits(P)  = region 内指向 region 外的边（已指向 Second 的除外）
动作      = exits 全部改指 Second；First/Second 两道门强制放行
```

跳过条件：region 为空 / 过大（>512 节点）/ 无出口 / 与非同类条件混配 / `partnerID<=0`。

## 二、两个「压制」机制（本次改造的核心）

| 机制 | 谁做的 | 作用点 | 目的 |
|---|---|---|---|
| **`relax_once`** | mod | 条件层 | 限制「放宽」能做几次。实现上**只第一次求值返回放宽，之后永远走原版** |
| **Hold 守卫（`[once]`）** | mod | 门层 | 「本次判定碰过队友条件 + `checkSucessTimes != 0` + 仍然通过」→ 压回 false，防放宽导致的门反复通过 |
| `checkSucessTimes` | 游戏原生 | 门层 | 关卡自带的次数上限，用于一次性事件 / 限次分支 |

### 目前的副作用

1. **守卫误伤**：角色真在队时门正常通过，也会被判定为「放宽引起的重复触发」而压制；
2. **虚假计数**：守卫压制前 `orig_hold_check` 已返回 true → 游戏的 `checkSucessTimes` 被真实 +1 → 加速消耗原生次数；
3. **与展平冲突**：展平希望「两侧各播一次」，守卫希望「只通过一次」→ 现在靠「压制后强制放行救回」打补丁；
4. **`relax_once` 粒度粗糙**：key 曾是「每图一次」（v160 起改为「每(图,pid)一次」），额度被**先求值的那条条件**吃掉，且常常被**预判轮询**白吃。

## 三、已定位的具体问题（实机证据）

### 3.1 现象

以 `R10049-2`（月咏樱羽「护花使者」）为例，两端表现一致：

| 角色 | 结果 | 原因（已证实） |
|---|---|---|
| 10084 / 10083 / 10078 / 10053 / 10075 | ✅ 内容播出 | 门对被展平，两道门 `forced=Y → 通过` |
| **10054** | ❌ 内容不播 | 其门对位于 **10063「石万三存在」分支内部**；挡住它的是 `EnterAreaCondition`（当进入场景区域），其中 **5 条 `times=1 不通过`**（原生次数用尽），14 条 `times=0 不通过`（区域判定本身不成立） |
| 20204 | ⭕ 按原版 | 条件是「判断地图存在NPC」，知府当时不在场 → 走「不存在」侧 |
| **10098**（-2-1 的 29 节点） | ❌ 内容不播 | 卡在 **`TalkToNpcCondition` ×5 全部不通过**（需先与 5 个 NPC 对话）：20243 甜食商贩 / 20231 太学馆馆长 / 42161 / 42162 / 42163 |

### 3.2 关键结论

- **展平只能重连「一对门内部的两侧」，无法让「上游本来走不到的分支」变得可达**；
- `10054` 的断点在**上游的不相关条件**（区域/次数），不在展平与放宽这一层；
- `10098` 的断点是**前置交互未完成**，与次数无关。

## 五、候选方案

### 方案 A：直接删除 Hold 守卫，全部交给 `relax_once`

- 优点：语义最简单，`times` 不再被虚假消耗，展平不必再「压制后救回」；
- 风险：**861 张含环的图**里，被放宽的门可能在同一次播放内反复通过 → 重复对白 / 死循环。原生 `checkSucessTimes` 能兜一部分，但它对「我们放宽过」的门是否还生效没有保证。

### 方案 B（推荐）：守卫降级 + `relax_once` 精确化

1. **守卫降级**：只在「该门既没被展平接管、也没被本次放宽」时才压制；
   - 展平的门 → 不再被压，也不再虚假 +1 `times`；
   - 放宽的门 → 由 `relax_once` 自己兜底（它天然只放宽一次）。
2. **`relax_once` 的 key 精确到条件**：`(图, 条件节点指针)`，且只对 `Negate=0`（"在队"）侧放宽；
   - 解决 173 个 pid 的「同图多对门共用额度」冲突；
   - `Negate=1`（"不在队"）侧本来恒真，放宽无意义，直接排除。
3. **`pid<=0` 的条件一律不参与**放宽与展平。
4. **额度按「播放窗口」发放**：剧情开始播放时重置该图的额度表；
   - 预判轮询不再白吃额度；
   - 播放结束后不重置 → 防止整段剧情反复触发。

### 方案 C：维持现状

- 保留两个压制，接受 `10054` / `10098` 这类「上游不可达」内容永远不播。

## 六、推荐方案（B）细节

```
┌ 条件层 ─────────────────────────────────────────────
│ 条件被求值（CheckAllConnectNode）
│   ├─ 命中名单（固定名单 / 图名 / 门对 / 场景级） → 原版
│   ├─ 该条件已在“本图本窗口额度表”中 → 原版
│   ├─ pid<=0 或类别不是「需要伙伴」 → 原版
│   └─ 否则：发放额度（记录该条件指针）→ 放宽
│
└ 门层 ───────────────────────────────────────────────
  HoldNode.CheckCondition
    ├─ 该门被展平接管 → 强制放行（不压制、不计次数）
    ├─ 该门对应的条件在本次窗口内被放宽过 → 不压制（交给条件层兜底）
    └─ 其余：保留现有守卫逻辑（碰过队友条件 + times!=0 + 通过 → 压制）
```

额度表的生命周期：

| 事件 | 动作 |
|---|---|
| 剧情开始播放 | 清空该图的额度表（发放新额度） |
| 同一次播放内 | 每个条件只能用一次额度 |
| 播放结束 | 保留（不重置）→ 防止整段剧情反复触发 |
| 读档 / 换档 | 清空（现有 `relax_once_reset` 已具备） |

## 七、风险与缓解

| 风险 | 可能性 | 缓解 |
|---|---|---|
| 含环图重复对白 | 中（861 张有环，但多数环由原生次数管着） | 守卫只对「未被放宽/未被展平」的门保留；先用 3~5 张典型图回归 |
| 苗彩蝶 `R10005-*` 循环回归 | 中 | 该图在 `k_fixed_original` 名单内，先验证 |
| 播放窗口判定不准（`StoryScenarioNode.OnActive` 是否覆盖所有播放路径） | 中 | 现有播放检测已覆盖主路径；独立剧情节点（`StoryOpenNode`）需确认 |
| 展平与放宽双重作用导致「两侧都播 + 条件恒真」 | 低 | 展平门的条件不再放宽（展平已强制放行，无需放宽） |
| 复杂度上升 | 中 | 拆成两次提交：先“守卫降级”，再“relax key 精确化”，各自可回滚 |

| S3 | 额度与播放窗口绑定 | ✅ 引入窗口重置点 | 同一图连续两次播放，第一次与第二次的放宽行为一致 |

## 九、验收标准

1. **不回归**：`R10005-*` 苗彩蝶不再循环；已正常播出的内容（10084/10083/10078/10053/10075）不受影响；
2. **额度精确**：日志中同一图内不同 pid、同一 pid 的不同门对，都能各自获得一次放宽；
3. **次数干净**：`[gate]` 里不再出现「压制后被救回」的记录，`checkSucessTimes` 不再被虚假 +1；
4. **行为可解释**：任何「内容没播」的情况，都能从日志定位到具体是哪类条件挡住（区域 / 交互 / 标记 / 次数），而不是「不知道怎么就没播」。

## 十、待决问题（需要讨论）

1. **守卫是否保留**？方案 A（全删）省事但有 861 张含环图的风险；方案 B 保留但降级。倾向 B。
2. **`relax` 的额度单位**：`(图, 条件)` 还是 `(图, pid, 侧别)`？前者最精确（推荐），后者实现更简单。
3. **播放窗口的判定点**：只用 `StoryScenarioNode.OnActive`，还是也要覆盖「独立剧情节点」`StoryOpenNode`？
4. **`10054` / `10098` 这类「上游不可达」** 是否要处理？
   - 现状：不处理（尊重原版区域/交互前置）；
   - 若要处理，只能放宽 `EnterAreaCondition` / `TalkToNpcCondition`，但那等于**跳过玩法前置**，不建议。
5. **名单体系**：`判断地图存在NPC` 等类别是否永久排除在放宽/展平之外？
