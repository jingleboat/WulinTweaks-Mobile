## 一、游戏原版：事件与剧情的实现方法

**依据：`D:\steamgame\steamapps\common\WulinSH\Wulin_Data\StreamingAssets\ModEditor\ModEditor_Doc\`
下的《事件编辑器帮助文档-节点说明.docx》《…-几个游戏内的事件逻辑解读.docx》（官方权威）**

### 1.1 两层结构

```
事件文件（逻辑层）  ── 调用 ──►  剧情文件（演出层）
```

**原文（节点说明 第 342 段）：**
> 剧情文件被事件调用，可以理解为事件文件承载的是整个事件的逻辑层，而剧情文件只是配合演出。

- **事件文件**：`.asset`，在 `Assets/GameRes/Story/`。节点有「流程判断」「播放剧情」「添加标记」「选项」「发生预设战斗」等。
- **剧情文件**：`.asset`，在 `Assets/GameRes/Scenario/`。节点是演出（对话、移动、黑屏、震屏…）。

### 1.2 事件文件的节点分类（按官方颜色）

**原文（第 143 段 / 第 288 段）：**

| 类别 | 颜色 | 入口/出口 | 行为 |
|---|---|---|---|
| 系统节点 | 红 | 固定 3 个 | 事件头、玩家获知事件、玩家进入事件 |
| 条件节点 | 黄 | 连在「黄色圆点」上 | 判断数值/背包/队伍/NPC 状态等 |
| **执行节点** | **蓝** | 1 进、1 或多出 | **立即生效** |
| **结果节点** | **绿** | — | **即时经过也不结算**，等「勾选了立即结算的流程判断」或事件完成时才结算 |

**这条区分很重要**，因为它决定了「展平跳过某个节点」的后果：

| 类型 | 举例 | 跳过的后果 | 何时暴露 |
|---|---|---|---|
| 蓝色执行 | 播放剧情、添加/删除标记、选项、发生预设战斗、伙伴邀请或离队、设置自定义变量 | 立即缺失 | 立即～短期 |
| **绿色结果** | 奖励、改变玩家货币、改变玩家势力、增减 buff、改变 NPC 关系值、显隐大地图图标 | **不结算 → 永久丢失** | 事件完成时 |

### 1.3 条件的「且」与「或」

**用户确认的规则（与文档第 119 段附近的图示一致）：**

```
或 = 多个条件节点 → 都连在同一个执行节点的同一个黄点
且 = 条件节点串联 → 其中一个再连执行节点
```

**注意：这是**条件层**的规则。门对属于**执行层**并联（见 1.5），两者不同层，不冲突。**

### 1.4 「流程判断」= 门

**原文（第 244~251 段）：**
> - 流程判断是最常用的节点之一
> - 「继续的条件」连接条件节点；**可以不配置，意为无需条件即满足**
> - 只有满足条件后事件才会继续向后走，否则玩家可以自由移动
> - 「立即结算」：事件中的结果节点不会立即结算，走过一个勾了立即结算的流程判断后才结算

**关键推论：**
- 门的 `conditionPort` 为**空** → **恒真**（官方明说「无需条件即满足」）
- 门的 `conditionPort` 连**恰好一个**条件节点（多个条件 = 串行门链，或并联门）

### 1.5 并联门必须互斥（**官方范式，本项目的核心依据**）

**原文（第 251 段）：**
> **当多个「流程判断」并联时，条件应当互斥，或都不满足。如果并联起来的多个「流程判断」同时出现条件满足，将无法确定该走哪一个分支。**

**《几个游戏内的事件逻辑解读》里 6 处实例全部强调「互斥」：**

```
27| 两个分支经过的条件是互斥，一个时间段的取反
32| 2个分支互斥，条件是敲钟是否大于等于10
34| 2个互斥分支，判定条件为大师兄是否死亡
38| 2个互斥分支，根据敲钟次数是否达到10
68| 2个互斥分支，以连胜次数10为条件
80| 11会分出4条互斥的分支，分别根据不同的仁德区间
```

**→ 门对（在队 / 不在队）就是「并联互斥」最典型的形式。**

### 1.6 剧情文件的执行模型

**原文（第 345 / 347 / 363 段）：**
> - 由多个分割线隔离成多个相对独立的区域，**每个区域的节点会同时启动**，当整个区域的节点全部拿到回调后，才会跳到下一个区域
> - 同区域内多个节点若要**顺序**执行，必须右键「链接」显式串联，否则同时启动
> - **对话（屏幕下侧）的回调 = 玩家点击屏幕**

**实证（`R10049-0_3_2.asset`）：**

```
节点 9 个 = 对话 × 4 + 分割线 × 4 + 根节点 × 1
```

**→ 4 句对话、区域串行、每句等玩家点击 → **不可能在几毫秒内播完**。**

### 1.7 「可重复播放」与最小间隔

**原文（第 250~253 段，在「玩家进入事件」节点下）：**
> 勾选「可重复播放」意味着，玩家走过了整个事件的最后一个节点，可以等待一段时间再次触发事件。最小间隔单位为刻，游戏内一天为 96 刻。

**注意：这是**事件级**冷却，与下面 6.3 讲的 `times`（HoldNode 的通过标记）**不是一回事**。**

## 二、门对：我们要处理的原始结构

### 2.1 门对的识别（代码 `find_pairs`，与离线工具一致）

**四条全部满足才算门对：**

1. 父节点 `OutPort` **恰好 2 条**连接
2. 两条连接指向的两个节点**都**是「队友条件」类：
   `需要伙伴` / `需要角色加入` / `是否加入过队伍` / `需要角色加入过队伍`
3. 两个条件的 `partnerID` 相同且 **> 0**
4. 两个条件的 `Negate` **互补**（0 = 在队 G0，1 = 不在队 G1）

**且：至少一侧直接接剧情节点（`story_exit`）。**

**第 2 条是硬要求**（v251 教训）——`partnerID` 字段不是队友条件专属，`判断地图存在NPC` / `当与Npc交互` / `改变NPC关系值` / `增减buff` 等都带它。早期只看 `partnerID + Negate`，导致 `R10049-2` 里石万三「在地点」和「不在地点」两段剧情被依次播放（原版只播一段）。

### 2.2 梯子链

**实测结构（`R10049-2-1`，4 对）：**

```
            P1 → [10061 G0(_4_2), 10061 G1]
                          ↓ G1 出边指向 P2
            P2 → [10075 G0(_4_3), 10075 G1]
                          ↓
            P3 → [10052 G0(_4_4), 10052 G1]
                          ↓
            P4 → [10098 G0(_4_5), 10098 G1 → _4_6（都不在队）]
```

**每对的 G1（不在队）门出边指向**下一对的父节点** → 形成「在队 → 播剧情 → 不在队 → 判下一个角色」的链。**

**关键：每对各有**独立父节点**，父节点之间是「G1 出边」串起来的。**

### 2.3 `region` 的定义

```c
region = reach(G0) − reach(G1) − {G0, G1}
```

**含义：只有在队才能到达的节点集合。** 也就是「这段剧情是角色在队时的专属内容」。

**v213 的关键修正（用户要求的「局部判断」）：**

```c
// flat_region 的 G1 侧 BFS
if (t == p->g0) continue;      /* v213：不穿过对方门（环形图的关键） */
```

**为什么必须：`R10049-2-1` 的剧情图整体是**环形**的（各段剧情写完标记后汇入同一个「流程判断」枢纽，枢纽又分给 5 个门，其中一道直接回到主链头 `_4_1`）。不加这一句，`reach(G1)` 会顺着环绕回 G0，把 G0 自己也划进去 → region 恒为 0 → 4 对全被判「没有独占内容」→ 从不展开。**

**加之后：4 对各自能算出 region = 2。**

**实测 region 分布（全库 651 对）：**

```
reg = 0      :  55 对
1 ~ 50       : 594 对
51 ~ 200     :   2 对
> 512        :   0 对      （从没触发过）
最大 reg     =  58
```

## 三、我们展开的期望效果

### 3.1 目标

**用户原话：「让本来能展开的展开」「播完所有梯子链场景」。**

即：一个门对，原版只播其中一侧（在队或不在队），展平后**两侧都播**（先在队、后不在队）。

### 3.2 三种状态（这是理解所有问题的关键表）

| 状态 | 放宽 | 展平 | 实际行为 | 评价 |
|---|---|---|---|---|
| **① 原版** | ✗ | ✗ | G0/G1 互斥 → **按是否在队各走一边** | ✓ 确定 |
| **② 放宽但不展平** | ✓ | ✗ | **两侧同时为真 → 引擎「无法确定走哪个分支」** | ✗ 未定义 |
| **③ 放宽 + 展平** | ✓ | ✓ | 并联改串联 → **两侧都播** | ✓ 目标 |

**状态 ② 的实测表现（`R10049-0`）：**

```
日志 L1033-1037：R10049-0_3_2 / _3_3 / _3_4 / _3_5 连续五行
而 _3_2 的剧情文件有 4 句对话（区域串行、每句等玩家点击）
→ 只能解释为：多个「播放剧情」节点被同时激活
→ 玩家看到画面混乱 / 只注意到一段 → 报「没播」
```

### 3.3 局部原则（用户明确）

> **原话：「注意局部成立即可，10061 那部分 10098 不在队接入的出口是一个循环图，但是那不是我们改线的范围，和我们没关系」**

**我们只改 `region` 内的出口边。region 之外的一切不是我们的责任范围，也不在验证范围内。**

## 四、展开的命中逻辑

### 4.1 逐对判定（4 条，全部满足才 ok）

| # | 条件 | 保证什么 |
|---|---|---|
| ① | `ex > 0`（有对外出口） | 有边可改；**隐含 `region > 0`**，不单列 |
| ② | `reg_n ≤ FLAT_MAX_REGION(512)` | 容量保护（防止吃掉共享的 `g_exit[8200]`） |
| ③ | 无 clash（region 不与同图其它对相交） | 两对改线不互相踩 |
| ④ | 所有出口边的目标：**除这条边外还有别的入边** | 防止下游变孤岛、整棵子树永久不可达 |

**关于 ① 的说明（用户指出后修正）：**

```
region = 0  ⟹  没有区内节点  ⟹  没有区内出口边  ⟹  ex = 0
所以 ex > 0  ⟹  region > 0
```

**因此 `region > 0` 被 `ex > 0` 完全隐含，单列是冗余。**

### 4.2 整链决策（这是 v271 新加的）

**规则：**

```
链内全部 ok  →  全链展开
链内任一不 ok →  整链不展开 + 整链不放宽
```

**为什么必须整链：**

- 全展开 → 并联改串联，确定
- 全不展开 + 不放宽 → 保持互斥，确定
- **部分展开 → 一边串联一边并联 → 状态 ② → 未定义**（官方第 251 段 + `R10049-0` 实测）

### 4.3 链的定义（宽松判据，用户要求）

**从任意一对出发，沿下列任一条边能串到的所有门对属于同一条链：**

1. 本对 `G1` 门出边 → 另一对的**父节点**
2. 本对 `G1` 门出边 → 另一对的 `G0` 或 `G1` 门

**用户原话：「10061 原版不同链，我们希望 mod 对这种情况能改为同链」→ 宽松判据正是为满足这条。**

**离线对比：**

| 判据 | 可展开 | 组数 |
|---|---|---|
| 严格（只认父节点） | 494 (75.9%) | 548 |
| **宽松（也认门）** | **489 (75.1%)** | **438** |

**宽松代价仅 5 对（0.8%），组数从 548 → 438（链更完整）。**

**关键图验证：**

```
R10049-2-1（4 对）→ 1 组 [10061, 10075, 10052, 10098]
R10049-0  （5 对）→ 1 组 [10088, 10009, 20063, 20025, 10021]
```

### 4.4 离线命中率（v271 规则）

```
门对总数            : 651
逐对 ok             : 497 (76.3%)
整链决策后展开      : 489 (75.1%)
被整链连带拦下的    : 162 对
链组数              : 438
```

## 五、展开的实现逻辑

### 5.1 阶段划分（代码 `flat_build`）

```
阶段 ①：算 region + 出口        （用原始图）
阶段 ②：逐对判定 → g_will_expand[]  （clash / 孤岛都在这里）
阶段 ③：整链决策 → flat_chain_decide() → 再改 g_will_expand[]
阶段 ④：只对 g_will_expand 为真的对改线
阶段 ⑤：未展开的对 → 条件进 g_pair_ban（禁止放宽）
```

**为什么可以「用原始图一次算完」：离线验证 209 张图，「原始图一次性判定」与「逐对改线逐对判定」**结果完全一致（0 差异）**。**

### 5.2 改线规则（三条）

**① 出口改指：**

```
有下一对（next_g0 ≥ 0）  →  出口边改指「下一对的 G0 门」
最后一对（next_g0 = -1） →  出口边改指「自己的 G1 门」
```

**② `G1 → G0`（只对有下一对的门对）：**

```
把本对 G1 门（不在队）的出边改指本对 G0 门（在队）
```

**目的：v237 实证「引擎在分叉点只走最后一条连接」，而 asset 里顺序是 `[G0, G1]` → 走最后一条 = G1 → 只播不在队。改指后无论走哪条都落到在队剧情，再由链式接续接力。**

**③ 最后一对不着 `G1 → G0`：**

**v245 教训：对最后一对也做 `G1→G0`，`10098` 的 G1 会指回自己的 G0 → `_4_5 → G1 → G0 → _4_5` 死循环，且 `_4_6` 永远播不到。**

### 5.3 策略 C（`G1→G0` 只改安全边）—— v271 修复

**原实现（v244~v269）把 G1 的**所有**出边都改指 G0 → G1 独占的下级子树全部不可达。**

**离线实测丢失（42 对 / 3046 个节点）：**

```
DBZX-6  pid=10083  49+52 节点（20 段剧情、删除标记×10、强制NPC死亡×6、选项×2）
M2190-3 pid=10064  43+43 节点（17 段剧情、获得/扣除背包物品×3）
M10140-3 pid=10086 12+18 节点（12 段剧情、预设战斗×2）
DNJH-6  pid=10008   6+12 节点（6 段剧情、改变NPC势力、显隐大地图图标）
```

**三种策略对比：**

| 策略 | 受影响 | 丢失节点 |
|---|---|---|
| A 全部改指（旧实现） | 42 对 | **3046** |
| B 只改「门对成员」 | 42 对 | **3046**（无效，下级本身就是门） |
| **C 只改「目标还有别的入边」** | **0 对** | **0** |

**判据的语义：**

- 目标还有别的入边 → 是**并联兄弟**（如 `10061 G1 → 10075 的门`，那个门还有父节点指着）→ 改指安全
- 目标只有 G1 指着 → 是**它独占的下级**（如 `DNJH-6` 的两个流程判断）→ 改指就切断

### 5.4 门表与强制通行

**两套机制：**

| 机制 | 粒度 | 效果 |
|---|---|---|
| `flatten_cond_always_true(cond)` | 条件节点 | 条件恒真（走基类 `CheckAllConnectNode`） |
| `flatten_gate_forced(gate)` | 门节点 | 门整体判真（`hook_hold_check` 兜底） |

**门强制**覆盖**次数压制**（`hold_check_core` 先跑，判假后由强制兜底返回 true）。**

**原因（v87 注释）：线已经改指了，若中途门又判假，就会「出口指向别处 + 门不放行」→ 剧情卡死。**

### 5.5 `g_pair_ban`（未展开的链禁止放宽）

**用户规则：「整组不展开时不放宽」，只针对门对。**

**实现：**

```c
// 整链决策后，未展开的对 → 其条件进 ban 表
for (k) if (!g_will_expand[k]) { flat_add_ban(g_cond[g0]); flat_add_ban(g_cond[g1]); }

// keep_original_for 开头查表
if (flatten_is_banned_cond(condNode)) return 1;   // 不放宽
```

**放在 TTL 缓存**之前**（禁放宽由图结构决定，不需要缓存）。**

**孤立门（不成对的队友条件）不进这张表，继续走原规则。**

## 六、放宽对展开的影响

### 6.1 放宽是什么

**用户确认：「放宽是条件恒真」。**

**实现（`hook_check_partner`）：**

```c
if (flatten_cond_always_true(self)) { ... return base_check_all(self, io, line); }   // 已展平的条件
if (F_STORY && base_check_all && !keep_original_for(self)) { ... return base_check_all(...); }  // 名单外的
```

**只挂在 `HavePartnerCondition`（`需要伙伴`）。**

**`IsJoinedTeamCondition`（`需要角色加入` / `曾经加入过队伍`）**不放宽**（v212）：**

**原因：放宽「曾经加入过」等于允许「从未加入」也能触发该角色的本命事件 —— 这正是「燕歌行从未入队、师父线照样触发」的一条通路。**

### 6.2 放宽为什么必须配套展平（核心逻辑链）

```
放宽（G0 与 G1 同时为真）
  ↓
违反官方设计范式（并联门必须互斥）
  ↓
引擎「无法确定该走哪一个分支」= 行为未定义
  ↓
实测（R10049-0）：多个「播放剧情」节点同时激活 → 玩家看不见
  ↓
补救 = 展平（并联改串联）
  ↓
展平失败 → 回到「同时为真」→ 又看不见
```

**所以：「只改命中范围、不改展开方式」在逻辑上不成立 —— 放宽一旦生效就必须同时改线恢复确定性。**

### 6.3 `times` 与次数压制

**事实（代码注释 + 反汇编结论）：**

```
HoldNode.checkSucessTimes(+0x70) = 「这个 Hold 已经成功过」的标志
addTimes() 置 1 / clearTimes() 置 0
但 CheckCondition()(0x3D9DEFC) 根本不读它
```

**→ 原版判定与 `times` 完全无关，它只是标记。**

**→ 「次数压制」是 **mod 自造** 的机制：**

```c
if (!F_STORY || !r) return r;                 // 原版判假 → 不管
if (g_team_cond_hits == before) return r;     // 本次没碰队友条件 → 不干涉
if (g_ev_relax_hits == 0) return r;           // 本次没真放宽 → 不压制（v211）
times = *(int*)(self + 0x70);
if (times == 0) return true;                  // 还没成功过 → 放行
if (图名 in k_fixed_original) return true;    // 例外
if (story_blacklisted(图名)) return true;     // 例外
return false;                                 // 压制
```

**目的：补「放宽绕过原版防重复」的窟窿 —— 否则一次性剧情会被重复触发。**

**与展开的交互：门强制（`flatten_gate_forced`）**覆盖**压制 → **已展平的门不会被压制** → 展平门无法靠压制打断环。**

### 6.4 放宽对「环形图」的影响（P3 的关键）

**环上的门会不会「必然为真」？只有三类恒真：**

| 门类型 | 恒真？ | 依据 |
|---|---|---|
| `HavePartnerCondition` 门 | **是** | 放宽 = 条件恒真 |
| 已展平的门 | **是** | 强制 true，且覆盖压制 |
| 无条件流程判断 | **是** | 官方：「可以不配置，意为无需条件即满足」 |
| **其它条件门** | **否** | 按原版（标记 / 物品 / 关系值 / 时间 / 区域 / **当与Npc交互**） |

**`R10049-2-1` 的实证：**

```
_4_5 → 添加标记 → 汇合点（region 外）→ 5 个门
                                        条件全是「当与Npc交互」
→ 需玩家点击 NPC 才放行 → 环不会自动绕回
```

**这就是为什么 v255 实测「`_4_5` 播了、`_4_6` 没播、不循环」，也是为什么「图论成环」判据永远误判（该图原版就有 9 个剧情节点在静态图上「成环」，实测却正常）。**
