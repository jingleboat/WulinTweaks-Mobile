### Q1（最关键）早期"能播"与现在"不播"的差异到底来自哪一处改动？

| B. 展平配对白名单收紧 | 15 对 → 12 对，改线 20 → 16 条，走线随之变化 | 只在展平开启时生效 |
| C. 对称化（v158） | 改线目标从"`Negate=1` 那道门"改为"父端口第 2 条连接" | 只在展平开启时生效 |

**未确认**：用户截图那一轮的"跳基类"补丁，在展平出现后是否被撤销、替换成现在的"有条件下放宽"。

### Q2 关掉展平后仍不触发，原因是什么？

若展平关闭，B/C 都不起作用，只剩 A 或 D。而 D 的四条在本图的通路上不参与（见 Q1 表格）。因此**若 A 也已不存在**，则目前没有能解释该现象的机制 —— 说明还有未识别的差异（例如早期版本的其他补丁）。

### Q3 走线为何在 `_8_0` 与 `_3_0` 两处发生分岔？

`_8_0` 之后早期走 `_8_1`、现在走 `_8_2`；`_3_0` 之后早期走 `_3_2` 链、现在走 `_3_1`。
**未知**：这两处分别由哪条连线/哪个节点的连接顺序决定；是否与"节点连接顺序在不同版本被改过"有关。

### Q4 展平配对判据"兄弟关系"是否成立？

我先前用一个"父节点集合相等"的检查得出"12/12 全部不是兄弟"的结论 —— **该检查方法过严**（把多入口的图误判），结论不可靠。
**需要**：改为按"是否存在同一个端口、恰好 2 条连线，分别指向两个门"来判定，再重新统计真兄弟对与误配对。

### Q5 放宽会作用于 `Negate=1`（否定侧）

当前 `keep_original_for` **未读 `Negate`**：当角色在队时，「不在队」条件也会被放宽 → 两侧同时为真 → 引擎按顺序取第一条 → 可能走错分支。
**需要**：加 `Negate=0` 过滤（两端同构）。

### Q6 额度粒度与两阶段消费是否必要？

现状：额度按 (图, pid)，首次求值即消费（v165 改为"原版失败才消费"），**预判轮询仍可能提前吃掉额度**。
候选：精确到 (图, 条件节点) + Available/Reserved/Consumed 三态；或绑定播放实例。

### Q7 守卫是否还需要？

守卫现只对"真发生放宽"的门生效。按设计，若额度足够精确（每段剧情一次、按需消费），事件不会恒真，守卫可能冗余。
**未验证**：删掉守卫后 `R10005-11`（苗彩蝶）是否复现循环。

### Q8 清陌生名的正确触发点

v164 因"展平门不调原版"导致 clear 漏跑（凌梦蝶显示陌生名）；v165 在门层补一次；v166 改为"播放期间门通过即清"。

## 十一、待办（TODO）

### T1　手机版「角色入水落点」改为「固定区间内随机」　✅ 已完成（v180，2026-11-03）

**v179 及以前的实现**（wulin-apk/native/src/water.cpp，最后一版是 v123 的 `2a2e781`）：

唯一真正生效的通道是 500ms 轮询 `force_poll`，它的选格函数是 `pick_water_cell()`：
遍历该图水域表，取**离她当前坐标曼哈顿距离最近**的那一格（并列取表里靠前的）。

```
force_poll（借 MapManager.IsBlock 的调用做节拍，每秒最多一次）：
  map 不在水域表 → return
  对名单每个 uid：
    GetCharacter(uid) 拿不到 → 跳过
    CurMapId != 当前图 → 跳过
    CurPos 命中水域表 → 跳过 ★
    选格 = pick_water_cell(CurPos)     // 最近水域格，确定性
    Role.NpcTP(选格); tick 偶数时 SetEndPos(keys[(tick*7)%count]); gci.SetPos(选格)
```

★ 这一句 `if (mask_has(e, x, y)) continue;` 是核心：**她已经站在任何水域格里（不管谁放的）就一句不动。**

因此 v179 的落点**既不是"固定一格"也不是"随机"，而是「跟着原版坐标走的最近水域格」**：

| 原版把她放哪 | v179 最终落点 |
|---|---|
| 陆地 | 离原版坐标最近的那格水域（原版坐标的确定函数） |
| 水里 | 原样不动（就是原版给的值） |
| 自己走上岸 | 拉回离岸边最近的那格，通常是刚才下水的位置 |

另外两个入口都是**死代码**，不产生任何行为：

| 入口 | 代码里的行为 | 为什么无效 |
|---|---|---|
| `hook_setmapid` | 取 `e->keys[e->count / 2]`（504 的 679 格 → `keys[339]` = (36,34)） | `hook GameCharacterInstance.SetMapId: 跳板构造失败`，**钩子从未装上** |
| `hook_setpos` | `pick_water_cell(e, x, y)` | `water_install()` 里只取函数指针、从不 `hook_install`，是纯死代码 |

> ⚠️ 更正（v181 记录）：v180 的提交信息与本节初稿写过「名单 24 个 uid 全部叠在 (36,34)」，**这是错的**——
> (36,34) 来自装不上的 `hook_setmapid`。会不会重叠取决于**原版给她们的坐标是否相同**：原版给同一坐标才叠，
> 给不同坐标就落在各自附近的格子上。

**v180 定案（用户拍板）**：

1. **随机粒度**：按 `(uid, mapId)` 哈希固定 —— 同一角色每次进同一张图落同一格，不同角色落不同格，不会叠在一起。
2. **范围来源**：**用户指定的矩形**，不自动取包围盒。
   - `504`：`x ∈ [16, 31]`，`y ∈ [23, 36]`（16×14 = **224 格，实测全部是水面、单连通**）
   - 因此是纯粹的整数取模，**不需要落空重试，也不需要"退回最近水域格"的兜底**
3. **其它地图不做落点覆盖**：`2160`（澡堂）、`2169`（空表）**保持原版生成坐标**；
   只保留「水面可走 / 入水形态」两层伪造（`mask_has` 那三处钩子是全图通用的，未加地图门禁）。

**为什么不用"整图包围盒"**（实测数据，`water_mask.h`）：

| 范围 | 水格 / 矩形格 | 命中率 |
|---|---|---|
| 504 **整图框** x[12,80] y[18,100] | 679 / 5727 | **11.9%**（两个水塘之间全是陆地） |
| 504 大水塘 x[12,45] y[18,43] | 502 / 884 | 56.8% |
| 504 小水塘 x[63,80] y[85,100] | 177 / 288 | 61.5% |
| **504 用户矩形 x[16,31] y[23,36]** | **224 / 224** | **100%** |

→ 整图框会把 88% 的采样落在陆地，且落点会在两块水塘之间乱跳；用户给的矩形恰好整块都在大水塘里，所以最优。

**实现**（`native/src/water.cpp`）：

- 新增宏 `SPAWN_RECT_MAP / _X0 / _X1 / _Y0 / _Y1 / _W / _H`；
- `spawn_rect_map(map)`：只有 `504` 返回 1，作为三个入口的统一门禁；
- `spawn_hash()`：Thomas Wang 32bit mix，保证 `(uid, map, salt)` → 稳定格；
- `pick_spawn_cell(uid, map, salt, &x, &y)`：矩形内取模。`salt=0` 是生成坐标，非 0 用于「游动目标」；
- 删除 `pick_water_cell()`（找最近，已无调用方）；
- 24 个 uid 在该矩形内哈希后的实测分布：**占用 24/24 格，0 冲突**。

**顺带修掉的既有缺陷**：旧代码的游动终点是 `e->keys[(tick*7) % e->count]`，会跨到另一块水塘
（504 有两块），A* 走不过去 → 角色停在原地播 `WashStand1`（泡澡坐姿）而不是 `WashMove1`（游泳）。
`tick*7 < 502` 时恰好都落在大水塘，所以前 71 次触发不会暴露，属于**潜伏 bug**；v180 改为在同一矩形内另取一格，由设计消除。

## 十二、504 漫游与水陆混合（v185 ~ v191，2026-11-03）

### 12.1 实测结论（都是设备日志，不是推断）

| 1 | **`Role.SetEndPos` 的跳板能构造**（`9 insn`），可以挂钩与调用 | `hook Role.SetEndPos: ok` |
| 2 | **NPC 漫游不走 `Role.SetEndPos`** —— 我们调它会被看到，游戏自己一次都没调 | v185：整场 `终点` 日志 10 条，全是我们的 |
| 3 | **`Role.PathMoveOnRoam(0x218779C)` 才是漫游驱动者**，每走一格重算一次剩余路径（格数递减） | v186：80 次调用，格数 40→39→38… |
| 4 | **AI 给的终点 100% 落在陆地，0 次落在水域** | v186：55 条 AI 终点全 `在水域=0`；落在水域的 25 条全部等于我们自己 `SetEndPos` 的目标 |

### 12.3 v191 最终实现（当前）

只用**已验证可用**的两样东西：`Role.SetEndPos` + 每秒一次轮询。不瞬移、不读位置、不改游戏数据结构。

```c
// 进场景后第一次轮询（约 1 秒，Role 生成完之后）
落点 = (uid,504) 哈希 → 矩形 x[16,31] y[23,36] 内一格
Role.NpcTP(落点)                       // 目的是把她摆进去；是否真生效未知，不影响结果
Role.SetEndPos(随机水域格)              // ← 初始 100% 命中，真正让她动起来的是这条
概率置 5%，5 秒后开始判定

// 之后每 5 秒（每个 uid 独立计时）
掷骰 prob%：
  命中 → Role.SetEndPos(新的随机水域格)，prob 重置 5%
  未命中 → prob += 5（封顶 100）
```

参数（`native/src/water.cpp` 顶部）：

| 宏 | 值 | 含义 |
|---|---|---|
| `SPAWN_RECT_MAP` | 504 | 只对这张图生效 |
| `SPAWN_RECT_X0/X1/Y0/Y1` | 16/31/23/36 | 落点矩形，**224 格实测全为水面**、单连通 |
| `SPAWN_RT_PERIOD_MS` | 5000 | 判定周期 |
| `SPAWN_RT_START_PCT` | 5 | 命中后的起始概率 |
| `SPAWN_RT_STEP_PCT` | 5 | 未命中累加 |
| `SPAWN_RT_MAX_PCT` | 100 | 上限，到即必中 |
| `SPAWN_BLOCKED_GUARD` | **0** | 「不可通行终点保底改写」暂时停用（整块不编进 .so，改 1 恢复） |

节奏（按上表算）：概率序列 5→10→…→100，**最迟 20 次判定（100 秒）必中**；
期望 5.29 次判定 ≈ **26 秒**一次；10 人同时在场 → 全场平均约 **2.6 秒**一次命中。

### 12.4 随机值怎么取

```c
static uint32_t rnd32(void) {          // 自己写的 xorshift32
    static uint32_t st = 0;            // 不用 libc rand：那是进程级全局状态，
    uint32_t x = st ? st : (st = (uint32_t)time(nullptr) ^ 0x9E3779B9u);
    x ^= x << 13; x ^= x >> 17; x ^= x << 5;   // 抽一次会扰动游戏自己的随机序列
    return (st = x);
}
static void pick_random_water_cell(int* ox, int* oy) {
    *ox = SPAWN_RECT_X0 + (int)(rnd32() % (uint32_t)SPAWN_RECT_W);
    *oy = SPAWN_RECT_Y0 + (int)((rnd32() / (uint32_t)SPAWN_RECT_W) % (uint32_t)SPAWN_RECT_H);
}
```

- **每次 `SetEndPos` 都现取新随机值**，无缓存；
- x、y 两次独立抽取 → 224 格等概率；
- 不校验"是不是水"：矩形 224/224 全命中烤表，取模结果必在水里；
- **范围只到矩形**：504 共 679 格水面，另有一块水塘 x[63,80] y[85,100]（177 格）永远不会被选中。

### 12.5 落点与终点是两套机制（不要混）

| 用途 | 取值 | 稳定性 |
|---|---|---|
| 落点（把她放进矩形） | `(uid, 504)` 哈希 | 同一角色每次启动固定同一格 |
| 终点（`SetEndPos`） | `pick_random_water_cell()` | **每次都是新随机值** |

### 12.6 仍未验证 / 未解决

1. **`Role.NpcTP` 是否真的改变她的位置** —— `get_CurPos` 不可信，没有可靠读位置的手段。
2. **AI 的目标池是否就是 PFM 的 `mLand`** —— 只是与 `probe.cpp` 的字段对应得上，没读过内容。
3. **`SPAWN_BLOCKED_GUARD` 停用后，"不可通行终点导致卡住"是否真的不存在** —— 未观察到卡住，但也没专门测。
4. `2160`（澡堂 / 177 格水面）现在完全不介入落点，只有水面判定生效。

### 13.5 「伙伴邀请或离队」的离队兜底：只有放宽有，展平没有

`Patch_ChangePartner`（v1.9.5）挂 `ChangePartnerNode.OnResult` 的 Prefix，**只认 `IgnoreTeamCondition`**（`Patch_ChangePartner.cs:33`）。
两个开关**默认值相反**：③ 放宽 = `false`、④ 展平 = `true`。
→ **默认配置下展平在跑、放宽关着，这个离队容错完全不生效。**

它兜的东西：remove 一个不在队的角色时，跳过原版 `OnResult`、视为已成功。

| 判据 | 行为 |
|---|---|
| `mode=ID` 且 `partnerID <= 0` | 视为成功，跳过 |
| `mode=ID` 且 `InTeam(pid) == false` | 视为成功，跳过 |
| `mode=队中位置` 且 `Index >= TeamSize` | 视为成功，跳过（释法寺 `School-2020-1` 就是 `mode=1 / Index=5`，队伍只有 2 人） |
| `PlayerTeamManager` 取不到 / `TeamSize` 越界 | 保守走原版 |
| 异常 | 走原版 |
| 该角色**真的在队** | 走原版，正常离队 |

**为什么跳过原版是安全的**：`ChangePartnerNode.OnResult` 本身是空壳 —— 反汇编（`0x3DA7878`，24 条指令）只有「类初始化守卫 → 取静态 `OnResultAction`（field `0x850`）→ null 就 `ret`，否则 `mov x1, x19(self)` 后 `br x3` 尾调」，对实例字段一个 `str` 都没有。

**展平路径没有这道兜底**，但见 13.6/13.7 的数据后判断风险有限，因此暂不改，仅记录。

### 13.6 `ChangePartnerNode` remove 分支的真实逻辑（反汇编 `0x269A964`）

```
w8 = self->mode (0x60)
if (mode == 0) {                        // 按 ID
    pid = self->partnerID (0x70);  if (pid < 1) return;
    chara = GetCharacter(pid);           // 取不建
} else {                                // 按队中位置
    idx = self->Index (0x64);  if (idx < 1) return;
    chara = GetTeamMemberByIndex(idx);
}
if (chara == null) return;               // ★ 实例不存在 → 彻底 no-op
w8 = self->state (0x74);
if (w8 == 1) goto remove;  if (w8 != 0) return;
// ---- add ----
AddCharacter(chara)                      // 返回值被丢弃
go = GetNpcObjectByTempID(pid)
if (go != null) { StopAutoMove(go); Destroy(go); }
return
// ---- remove ----
RemoveCharacter(chara, ItemType(0x7F7C000), false)   // 返回值被丢弃
if (MapManager.mCurMapID(0x94) != chara.m_curMapId(0x180)) return;   // ★ 只看"在不在当前地图"
ForceClearSeatSpace(chara.m_curPos(0x188))
CreateNpcByAutoSetLine(chara, forceUpdatePos:true, immediateMove:false)
```

**`AddCharacter` / `RemoveCharacter` 的返回值都被丢弃** —— 原版根本不看"队伍满不满""人在不在队"。所以「队伍已满时剧情要加人」不会出错，因为它连结果都不检查，加不进就静默失败。**这是"根本不看结果"，并非"游戏加了满员判断"。**

字段偏移（dump.cs 核对）：

| 对象 | 偏移 → 字段 |
|---|---|
| `MapManager` | `0x94` = `mCurMapID` |
| `GameCharacterInstance` | `0x180` `m_curMapId` / `0x184` `m_targetMapId` / `0x188` `m_curPos` / `0x194` `m_targetPos` / `0x1B0` `m_dir` |
| `CharacterPoolData` | `0x20` `NameAsStranger` / `0x28` `SurName` / `0x30` `GivenName` |

> ⚠️ 曾把 `0x94` / `0x180` 误读成"队伍人数 / 队伍序号"。真实语义是**地图 id** —— 那个 `cmp` 判的是「她在不在玩家当前加载的**地图场景**」，跟事件图、队伍都无关。

### 13.7 `RevertNpcObj` 的真实实现（反汇编 `0x23A8EEC`）

`CreateNpcByAutoSetLine` 开头会调它并短路，但**它不是"什么都不做"**：

```
line = <按 npc->m_instanceId(0x94) 查到的 line 配置>
if (line->0x10 != MapManager.mCurMapID) {          // 目标图 ≠ 当前图
    if (line->0x1c != 4) { w21 = 0; return false; }
    SetMapId(npc, line->0x10)        // ★ 写 m_curMapId
    SetPos(npc, line->0x30)          // ★ 写 m_curPos
    npc->m_dir(0x1B0) = line->0x38   // ★ 写朝向
    w21 = 0; return false;           // 返回 false，但三个存档字段已经改了
}
// 同图这一支
if (line->0x28 == 0) → 另一支
if (line->0x1c != 4) → 另一支
w21 = 1;
CreateNpcByAutoSetLine(npc, 1, 1, null);   // 递归回调
return true;                                // ← 外层据此短路
```

整个函数只有一个 `ret`（`0x23A9380`），返回 `w0 = w21 & 1`。

**含义**：`tbnz w0,#0 → return` 不是「不动」，而是「**她已经按 line 配置被还原好了，外层别再生成**」；而返回 false 的跨图分支是**改完三个存档字段之后**才返回 false。

对"假离队"（人本不在队）的结论：**不会损坏，最坏是"她的 `m_curMapId`/`m_curPos`/`m_dir` 被按剧情 line 配置重设一次"**。这一步跟"在不在队"无关，只看"在不在当前地图 + line 类型是否为 4"。

### 13.8 名字变成 `OutPort`：v90 之前的裸指针 UAF，已修，存量不修

**现象**（11 个存档全部解密对比）：

| 存档 | 实例数 | 20025 花四娘 | 20063 | 10088 |
|---|---|---|---|---|
| AutoSave1 / AutoSave2 | 1924 | `@风韵犹存的女子` | `@群芳馆·馆主` | `@温柔典雅的女子` |
| **Save2 / Save3 / Save4 / Save5** | 2050~2103 | **`OutPort`** | **`OutPort`** | **`OutPort`** |
| AutoSave0/3/4、Save0/1 | 3867~3883 | `''` | `''` | `''` |

三个角色全是 `m_surName=''` + `m_givenName='OutPort'`（干净档里 `m_surName` 也是 `''`，只有 `m_givenName` 坏）。
**Save2 已污染，远早于 `join`** —— join 日志显示 `解除陌生：本来就不是陌生状态，跳过`，压根没执行 `SetGivenName`。

**归因（沿用 v90 当时的记录，不是新推测）**：

1. v90 之前 `rn_apply_rename` 把实例的 `@陌生名` 覆盖成模板真名，原始名以**裸 `void*` 缓存在 `static RN_SLOT g_rn[]`**（C++ 静态数组）。
2. 字段被覆盖后，那个 `@xxx` 字符串对象**没有任何 GC 根引用** —— 而 C++ 静态数组里的裸指针 **Boehm 不扫描**（只扫托管堆 / 栈 / 寄存器 / 注册静态根）→ 被回收。
3. `rn_restore_rename` 到期时把**已释放的指针**写回 `m_givenName`。
4. 占用那块内存的正是 mod 自己：`flatten.cpp:120` 每次展开剧情图都 `A_string_new("OutPort")` / `"conditionPort"`。

`wulin_main.cpp:991-998`（v90 注释）原文记的就是这个机制，并写明"于是人物名字就显示成 OutPort"。

**排除现行版本的「显示真名」**：`rn_sync()` 在 **v148 被 `return; #if 0` 整段停用**（`wulin_main.cpp:1529`），`rn_apply_rename` / `rn_restore_rename` / `rn_patch_tpl` 都已成死代码。当前唯一还在写 `m_givenName` 的是 `unstranger_apply_uid`（`wulin_main.cpp:1888`），它写的是 `A_string_new("")` —— 但那是写进**托管对象字段**，字段本身是 GC 根可达的，不会像静态数组里的裸指针那样被回收。

**与实测一致**：这段剧情之后新触发的剧情，生成的实例没有被污染 → 当前版本不产生新污染。

**结论：只防新增，不治存量。** 存档里已经是 `OutPort` 的值没有被任何人修（`rn_restore_rename` 需要内存里的 `renamed` 标记，重启就没了），会一路跟着存档走。按用户决定**不做修复**。

### 13.9 本轮明确不改的三件事

1. **不给展平加 `Patch_ChangePartner` 的兜底** —— 后果只是"离队动作彻底 no-op"，不是卡死（展平自身把两道门都强制判真，流程必然继续）。
2. **不给展平加结缘图白名单** —— 12 张结缘图已测全且 region=0，用户决定不加。
3. **不修存档里的 3 个 `OutPort`** —— 现行版本不产生新污染，存量只影响显示。

## 十四、v1.11.65 / v194：展平白名单 + 链式停用（2026-11-04）

这一节是"开了分支展开后某些事件触发不了"这件事的收口。**所有结论都有离线数据或反汇编支撑**，
并且推翻了第十三节里两条靠推测写下的判断。

### 14.1 结论速览

| 问题 | 原因 | 处置 |
|---|---|---|
| PC 开「分支展开」后无关剧情不触发 | 名单式**链式接续**把角色内容末端接走，原出口被丢弃。`R10005-5` 丢掉的是「**时间流逝 Num=8**」→ 游戏时间不推进 → 靠时间开窗的事件全部错位（`R10136-5` 就是这样） | 链式接续**停用** |
| 手机同样不触发（移除名单后依旧） | 手机端 `flatten_relax_allowed` 是**白名单**，且 `relax_ok_add` 只写在"改线成功"分支里 → 门对改不了线的图，整张图队友条件全不放宽。PC 对应实现有 `_processed` 兼容口子（有门对的图永远进不去）→ 实际从未生效 → 所以只有手机出问题 | 手机端改为**恒放行**，与 PC 对齐 |
| 该展开的展开不了 | 保护太粗会误伤 | 用**白名单**而不是黑名单，实测仍可改线 **717/902 = 79%** |

### 14.2 PC 端链式接续为什么必须停

名单：`M5061-5 / R10005-5 / R10049-2-1 / R10098-1 / Role5-10 / M5061-3 / R10039-6`（v1.11.57/58 加）。

旧 `ApplyChain` 只前瞻一层，且只认「添加标记」「追加简介」两个节点名：

| 图 | 内容末端之后 | 旧实现结果 |
|---|---|---|
| `R10049-2-1` | 添加标记 | 认出来 → 改它的出口，标记保留 ✓ |
| `R10039-6` | 追加简介 | 同上 ✓ |
| **`R10005-5`** | **时间流逝 `Num=8`** | **没认出来 → 改它前面那条边 → 时间流逝被整个跳过** ✗ |
| `M5061-5` | 播放剧情 `M5061-5_17` | 没认出来 → 那段剧情被跳过 ✗ |
| `Role5-10` | — | 死配置（图里找不到那两个 pid 的门对） |

`R10005-5` 那三个「时间流逝」节点的参数是从剧情资产直接读的：`Num=8`、`fastForwardOptions=-4`。
`TimeGrowNode` 的字段就是 `Num`（推进量）+ `fastForwardOptions`，**这是存档级时间推进，不是界面动画**。

### 14.3 但"链式接续要解决的问题"本身不存在

它当初是为了解决「放宽后 p 的支线演完就结束、后一个角色的门轮不到」（v171 注释里的 `R10049-2-1` / 10061 → 10098 鱼薇儿）。
用同一份资产实测，**这个前提不成立**：

1. `tools/audit_chain_patch_v2.py`：名单 13 条里 **11 条的 region 为空**
   （region = `reach(G0) − reach(G1)`，即该角色的独占内容）→ 放宽这些对根本不改变后续走向。
2. `R10049-2-1` 的实际连线：

```
播放剧情 R10049-2-1_4_2   （10061 的剧情）
  → 添加标记            [入边=1]
    → 流程判断          [入边=9]        ← 所有角色的支线汇回同一个分派门
      → 流程判断(pid=20243/20231/42161/42162/42163…)
        → 播放剧情 _1 / _2 / _3 / _4_1 / _4_7 …
```

**所有角色的支线本来就汇回同一个共享分派门，10098 的门自然会被问到。** 不存在"死支线堵死后人"。

所以链式接续是在解决一个不存在的问题，代价却是实打实的时间流逝丢失 —— 停用，代码与名单保留待以后单独验证。

### 14.4 展平改成白名单（两端）

改线的本质是「把 region 对外出口改指到不在队门」，**原目标被跳过**。
只要原目标写存档级状态，跳过它就影响别的图。这是"局部改线影响全局触发"的唯一通道。

**必须是白名单而不是黑名单**：剧情资产不止 `ModEditor.zip`。例如 `R10136` 一族 **280 个资产**在
`aa/config_assets_all.bundle` 里（`catalog.json` 可查），黑名单靠"列出所有写状态的节点名"必然漏。

| | 允许被跳过的只有 |
|---|---|
| 流程判断 | `HoldNode` 纯分支 |
| 选项 | 玩家选择分支 |
| 注释 | 不执行 |
| `StoryScenarioNode`（「播放剧情」入口） | 跳过 = 这一段不播，与"原版 if/else 只播一段"语义一致 |

全量统计（`tools/audit_safe_skip_whitelist.py`，仅 `ModEditor.zip` 1804 张）：

| 被拦 | 185，原因：改变NPC关系值 47 / 发生预设战斗 20 / 添加标记 16 / 追加简介 13 / 改变江湖历练 11 / 删除标记 11 / **时间流逝 6** / 写入记事本 6 … |

### 14.5 手机端"不放宽"的确切证据


| **有门对的图** | **永远进不去 `_processed` → 第一行就 return true → 实际从未生效** | **严格执行白名单 → 不放宽** |

所以 `reach(10061 在队门)` 会经 `_4_2→标记→7282→42162门→_4_1→10061门` 绕回来，

### 局部去环方案（未实施）

**思路：算可达性时，禁止穿过这对门自身。**

当前 `flat_mark_reach` 是普通 BFS，从 G1 出发会经 `7282→42162→_4_1` 绕回 G0，

**需要的改动**：给 `flat_mark_reach` 加一个「禁止节点集合」参数，
只在 `flat_region` 内部调用时传入 `{G0, G1}`；`side_has_story` 那条调用保持原样。

**风险**：这会让所有原本 region=0 的门对突然变成 region>0，
展平开始对它们改线 —— 影响面比现在大得多，必须先在离线模拟（`tools/simulate_flatten.py`）
上统计会多展开多少对、其中多少是环形的。**没有离线验证前不要动。**

### 读档 / 新开档表现不同的真正原因

**不是「读档 vs 新档」本身，而是同一张图在两条路径下 `OutPort` 的连接顺序不一致。**

引擎行为（v237 实测确认）：

> **门（`HoldNode`）的 `OutPort` 有多条连接时，引擎只走最后一条。**

而 `_4_1` 这类「入口剧情」节点**不在任何 region 里**，展平从来没改过它的出口，
它的连接顺序保持 Unity 反序列化时的原样：

- **新开档**：顺序为 `[G0, G1]` → 走最后一条 = **G1** → 直接进「不在队」链 → 只播 `_4_6`
- **读旧档**：图重建后顺序恰好相反 `[G1, G0]` → 走最后一条 = **G0** → 播 `_4_2` → 链式接续正常

**顺序为什么会变**：`port.connections` 是 `List<DialogNodePort>` 反序列化的产物，
图对象重建 / 复用时元素次序并不保证与 asset 中一致。这解释了为什么行为
「时好时坏」，且与操作路径相关。

**v244 彻底消除了这个不确定性**：把 G1 门的出边全部改指 G0 门后，
**无论引擎走哪一条分叉，最后都落在在队剧情上**，再由链式接续接力到下一对。

### 待办 3：修 `libwulin.so` 的版本号

**目标**：让日志第一行能反映真实版本，而不是永远显示 `libwulin.so v179 已加载`。

- 无法从日志判断当前跑的是哪个构建

**现状代码**（`wulin_main.cpp` 启动日志处）：

**实现思路**：

1. **版本号改成编译期宏**，由构建脚本注入：

```c
#ifndef WL_VERSION

LOGI("=========== libwulin.so %s 已加载 (pid %d, 游戏 %s) ===========", WL_VERSION, ...);
```

```powershell
$ver = (git -C $repo rev-parse --short HEAD) + "-" + (Get-Date -Format "MMdd-HHmm")
```

### 四、v251 修的那个真 bug（用户发现）

**现象**：新开档走到 `R10049-2`，石万三（10063）「在地点」和「不在地点」两段剧情**依次播放**。

### 五、v253 修的死循环（用户发现）

**现象**：`R10049-2-1` 的 `_4_2 → _4_3 → _4_4 → _4_5` 重复播放 12 次。

**根因**：v229 为排查「图被误判 done」加的 `flat-force`（让该图绕过去重、最多重扫 8 次）。**重扫是破坏性的**：

```
第 1 次：门对 4 对，改线 14 条，链式接续全部正确
第 2 次：图已被改过 → 门对只识别出 1 对 → 它成了「最后一对」
        → next_g0 = -1 → 回落自己的 G1 门
        → 而 G1 在 v244 已被改指 G0
        → 剧情 → 标记 → G1 → G0 → 剧情 …  死循环
```

**教训**：**展平的改线不是幂等的** —— 第二次扫描看到的是改过的图，配出的门对集合不同，改线目标也就不同。任何「允许重复处理同一张图」的机制都必须极其谨慎。v253 已删除该调试代码。

## 二十四、展平的四类副作用与判断方法（2026-11-06）

> 这一章回答「剧情分支展开最需要注意什么」。四条里第 ③ 类是这轮实际修得最多的，第 ④ 类后果最重。

### ① 存档标记被跳过 —— 后果延迟显现，最难查

**机制**：region 出口改指别处时，如果「添加标记」节点落在被跳过的路径上，标记就没设上。

**为什么难查**：**当时剧情正常播完、没有任何报错**。几小时后玩家才发现「某个任务接不到」「某扇门打不开」「某个 NPC 不出现」—— 而这时代码早已跑过几万行。

**最典型的教训（v50）**：`EJ-004 大梁捞朱` —— 放宽让「洛天雄在队」判真 → 对话播完 → 接着的 `ChangePartnerNode(remove)` 要把他踢出队，**可他本来就不在队**，动作落空 → 后面那对「他在队 / 他不在队」的流程判断两条都进不去 → 剧情彻底卡住。

**对策**：`hook_change_partner` 里「remove 一个不在队的角色」当成功处理，不调原版（反汇编确认 `ChangePartnerNode.OnResult` 本身是空壳）。

### ② 流程分支丢失 —— 内容缺失

**机制**：改线改变「原来走哪、现在走哪」。四种具体来源：

1. **region 出口改指别处** → 原方向的内容不再走到
2. **链式接续的「下一对」推断错** → 中间那段的剧情被跳过
3. **错误地改区内边**（而非区外出口）→ 下游整条效果链被切断
4. **G1 分支变孤岛** → 见下面的「36 对为什么不救」

**判断方法**：离线跑两个检查
- 改线后本对 G0 剧情是否仍可达
- **G1 可达集的内容是否变不可达**（这一条我早期漏了，导致方案出错，见第五节）

### ③ 循环 / 重复播放 —— 实际最高发，玩家会卡死

**比①②更危险**：标记丢了只是内容缺失，**循环会让玩家卡住、无法继续**。

**这一轮修的五次：**

| 版本 | 现象 | 根因 |
|---|---|---|
| v244 | 最后一幕无限循环 | G1→G0 对「最后一对」也生效 → `_4_5 → G1 → G0 → _4_5` |
| v246 | 开场剧情循环 20+ 次 | 改指「同一段剧情」的 G1 → 绕回自己 |
| v252 | `_4_6` 提前触发、`_4_1~_4_5` 全不播 | region 从 20 缩到 3 → 出口位置从「5 个单人门之后」提前到「汇合点」 |
| v253 | `_4_2~_4_5` 重复 12 次 | `flat-force` 重复处理 → 第二次配出的门对变少 → `next_g0=-1` → 回落 G1 → 死循环 |
| v256 | 全库 24 处潜在环 | 最后一对改指 G1，而 G1 能绕回本对剧情 |

**判断方法**：离线跑「原版无环 → 改线后有环」的逐节点比对。这次正是靠它发现 24 处。

**根本教训**：**展平的改线不是幂等的。** 第二次扫描看到的是改过的图，配出的门对集合不同，改线目标也就不同。任何「允许重复处理同一张图」的机制都极其危险（v253 的 `flat-force` 就是这么翻车的）。

### ④ 图结构被写坏 —— 操作失误型，后果最重

**不是设计副作用，而是改代码时容易犯的错。**

**v241 实例**：用 `g_rewire[]` 里记录的旧 `port` 指针还原改线 —— 读档后图重新加载，**那些对象早已释放**，往失效地址写「节点引用」等于**往随机内存塞对象的内部指针**，把图结构写坏。之后所有门判定失效。

**对策**：图重载后绝不使用旧指针。读档时既不清表也不还原（改线本来就会随图重载自动丢失）。

**每次打包的机械检查**：`.dynsym` 里任何未定义符号若以 `g_*` / `A_*` / `orig_*` / `F_*` 开头，`dlopen` 会静默失败 —— **mod 完全不加载，游戏却正常能玩**（v220~v222 因此白跑好几轮测试）。

### 五、修正：曾提出的「分叉点改指 G0」方案已作废

**曾以为**：无出口的门对，只要把「分叉点 → G1」那条连接改成「→ G0」，就能让在队剧情播出来。离线看起来很好（73 对里 37 对可救、剧情不可达 0、新增环 0）。

**实际错在**：**只验证了「本对 G0 剧情是否可达」，没验证「G1 分支的内容去哪了」。**

**`Def-2040` 的真实结构拆穿了它：**

```
G1门(不在队) ─┬→ 流程判断A → 选项 × 5          ← 5 个玩家选择分支
              └→ 流程判断B ─┬→ 流程判断 → 执行剧情(_12)
                            └→ 流程判断 → 执行剧情(_13)

G1 可达集：14 个节点
  剧情：执行剧情(_12)、执行剧情(_13)
  效果：发生预设战斗、添加标记、选项 ×5
```

**G1 只有一个入边（就是分叉点那条）。把它改指 G0 = G1 变孤岛 = `_12`/`_13` 两段剧情、5 个选项分支、一场预设战斗全部丢失。**

**所以方案撤回。无出口的 79 对保持现状：不展开、走原版路径、放宽后走 G1 播「不在队」内容。**

**这其实是原版设计**：`Def-2040` 里 `_11`（在队版）和 `_12`/`_13`（不在队版）本来就是互斥的两条路。放宽让它走了不在队那条，**内容完整，只是不是「在队版本」**。要让两者都播，只能改 asset（重写图结构），不是运行时能解决的。

**这也是「改 asset 结构」和「改运行时接线」的分界线** —— 前者能表达任意顺序，后者只能重排已有的边。

### 27.4 `times` 的真相（`OFF_HOLD_TIMES = 0x70`）

### 28.3 B 规则（逐对 ok + 整链决策）

**逐对判定（只算不改）：**

```
ok = (region > 0)                                ① 有独占内容
   ∧ (ex > 0)                                    ② 有对外出口
   ∧ (无 clash)                                  ③ 不与同图其它对 region 相交
   ∧ (所有出口边目标：除这条边外还有别的入边)      ④ 防孤岛（丢下游）
```

**整链决策：**

```
链内全部 ok  →  全链展开
     ① 出口改指「下一对的 G0」；最后一对改指自己的 G1
     ② G1→G0：**只改「目标还有别的入边」的边**（策略 C）
     ③ 登记门表（强制通行）+ 允许放宽

链内任一不 ok →  整链不展开 + **整链不放宽**
     ① 不改线
     ② 登记「禁止放宽」（新增表 g_pair_ban）
     ③ 回到原版：G0/G1 互斥，按「是否在队」各走一边
```

**「整链不展开 + 不放宽」的直接后果（三态表）：**

| 状态 | 放宽 | 展平 | 行为 |
|---|---|---|---|
| ① 原版 | ✗ | ✗ | 互斥 → **按是否在队各走一边** ✓ |
| ② 放宽但不展平 | ✓ | ✗ | **同时为真 → 引擎行为未定义** ✗ |
| ③ 放宽 + 展平 | ✓ | ✓ | 串联 → 两侧都播 ✓ |

**只针对「门对」。孤立门（不成对的队友条件）不进任何一张表，继续走原规则。**

### 28.4 实现前必须验证的三条安全性质

**目标：展开后不会导致「某个流程/事件固定触发不了」「异常中断」「一直循环触发」。**

**P1 可达性（不固定触发不了）**
- 形式化：对每个原版可达的节点 `v ∈ V`，改线后仍从入口可达
- 最小要求：**所有剧情节点（`播放剧情`/`执行剧情`）与原版终点可达**
- 相关规则：④ 孤岛判据、策略 C

**P2 不死锁（不异常中断）**
- 形式化：从入口出发的任何执行路径，都能走到「终止节点」（无出边，或所有出边判假时自然停）
- 风险来源：改指的目标门**不放行**（未展平 → 不放宽 → 判假）→ 路径在那里断
- 相关规则：整链决策（全展开或全不展开）

**P3 不无限循环（不一直循环触发）**
- 形式化：改线后不存在「从某节点出发能回到自己、且环上的门**必然为真**」的路径
- **关键：放宽让 `HavePartnerCondition` 恒真** → 环上若全是这类门 → 必然循环
- **另有：`flatten_gate_forced`（已展平的门强制 true）会**覆盖**次数压制** → 展平门无法靠压制打断环
- 相关规则：需新增判据

### 28.8 修正：`region > 0` 是冗余条件，B 规则里删掉（2026-11-06，用户指出）

**用户指出：「我们之前论证了 region = 0 判断是不必要的，为什么现在需要更严格的 region > 0 判断」**

**这是我在 28.3 里的逻辑矛盾，已修正。**

**推导：**

```

```

**因此 `region > 0` 被 `ex > 0` 完全隐含，单列是冗余 —— 等于把 28.1 里判定为「可删」的那个判断又写回去了。**

**B 规则的正确形式（修正后）：**

```
ok = (ex > 0)                           ① 有对外出口（隐含 region > 0）
   ∧ (reg_n <= FLAT_MAX_REGION)         ② 容量保护（防吃掉共享的 g_exit[8200]）
   ∧ (无 clash)                          ③ 不与同图其它对 region 相交
   ∧ (所有出口边目标：除这条边外还有别的入边)   ④ 防孤岛
```

**`region > 0` 不单列。**

**实现时同样按此形式：**
- **`FLAT_MAX_REGION` 上限检查保留**（容量安全网）
- **不额外加 `region > 0` 检查**（`ex_n == 0` 已覆盖）
