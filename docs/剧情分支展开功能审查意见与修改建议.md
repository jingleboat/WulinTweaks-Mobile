# 剧情分支展开功能审查意见与修改建议

**审查对象：**《展开机制审查.md》描述的 v271 分支展开方案\
**审查性质：** 设计与静态逻辑审查；不等同于待测源码逐行审计或实机验证。

## 1. 审查范围与重要修正

本意见以用户提供的 v271
机制文档为主要依据。公开仓库尚未同步待审版本，因此旧仓库代码只用于理解历史实现，不用于判断
v271 是否实现某项功能。

**重要修正：门对识别条件已经收束为只有「当前在队」条件。**
因此，先前关于 `IsJoinedTeamCondition`
被识别为门对并被门级接管绕过的风险，不再作为 v271
当前设计缺陷。建议将这一收束落实为代码中的严格类型白名单：只接受
`HavePartnerCondition`（当前在队），其他条件类型一律不得进入展平流程；`IsJoinedTeamCondition`
继续走原版判定。

## 2. 总体结论

v271 的总体方向合理：基于原始图计算每对门的 `region`
和出口，先逐对判定，再进行整链决策，最后只对获准的门对实施改线，并对未展开门对禁止普通条件放宽。

文档报告的离线结果：

-   门对总数：651
-   逐对判定可展开：497（76.3%）
-   整链决策后可展开：489（75.1%）
-   被整链连带拦下：162 对
-   链组数：438
-   `G1→G0` 下级切断问题：旧实现 42 对 / 3046 节点，v271 报告为 0
-   出口孤岛：旧实现 19 对 / 26 节点，v271 报告为 0

这些数字说明新规则在当前离线快照中减少了已知结构性损失，但不能直接证明运行时播放顺序、结果结算、重复播放和异常恢复均安全。

**审查结论：建议继续推进，但实机测试前应补强整链结构约束、策略 C
的替代路径证明、节点顺序与结果结算验证，以及运行时改线原子性。当前不应优先追求覆盖率。**

## 3. 重点审查意见

### 3.1 门对识别：收束到当前在队条件是正确方向

当前识别器应严格限定为：

-   父节点存在符合预期的两条分支；
-   两侧条件均为 `HavePartnerCondition`；
-   两侧 `partnerID` 相同；
-   两侧 `Negate` 互补；
-   满足文档规定的直接剧情节点等结构要求。

还应增加以下拒绝条件：

1.  `conditionPort` 不是恰好一条合法条件连接时，拒绝该门对。
2.  条件节点类型不是明确的 `HavePartnerCondition` 时，拒绝该门对。
3.  条件节点、门节点或连接目标无法完整读取时，拒绝该门对。
4.  连接目标不属于当前图，或扫描到的连接数与实际连接数不一致时，拒绝该图的展平。
5.  任一扫描、数组容量或改线记录容量不足时，整图保持原版，不得部分登记强制放行门。

原因是门级强制放行会改变整个 Hold 的条件结果。如果 Hold
的条件端口包含额外的时间、区域、标记或其他条件，只凭其中一个当前在队条件识别并接管整个门，可能绕过其他原版限制。

**识别原则：宁可漏识别，也不要在条件结构不完整时接管门。**

### 3.2 整链分组：连通关系不等于线性播放顺序

v271 的宽松链定义允许沿 `G1` 出边连接到另一对的父节点、`G0` 或
`G1`，从而将更多门对归入同一组。这有助于覆盖原本被严格父节点关系拆开的门对，但它证明的是门对之间存在连接关系，不必然证明这些门对构成唯一线性顺序。

例如：

``` text
          P1
         /  \
        P2  P3
         \  /
          P4
```

这是一个连通的门对依赖结构，但包含分叉和汇合。仅把它们放入同一个链组，不能回答
P2 与 P3 的先后顺序，也不能证明两条分支都能保留。

**建议把"链组识别"和"可安全线性展开"分成两个步骤：**

-   第一步：按现有宽松关系构建门对依赖图，得到连通组。
-   第二步：对每个组检查是否满足可线性展开条件。
-   只有满足条件的组才允许展开；其余组整组跳过并禁止普通放宽。

第一阶段建议只接受简单路径：

-   唯一起点、唯一终点；
-   每个门对最多一个前驱、最多一个后继；
-   不存在门对级环路；
-   每条依赖边都能确定唯一后继关系。

分叉、汇合、交叉依赖和环形依赖先不自动展开，待有明确的多分支调度语义后再扩展。

### 3.3 策略 C：目标存在其他入边只是初筛，不是安全证明

v271 对 `G1→G0` 采用选择性改线，避免旧实现把 G1 的所有出边都改向
G0，进而切断 G1
独占的下级子树。当前判据要求出口目标除当前边外还存在其他入边。

这比无条件改线更安全，但"存在其他入边"不足以证明替代路径在本次改线后的事件执行中可达。

``` text
        A（当前出口）
         \
          X → 后续剧情
         /
        B（另一入边）
```

虽然 X 还有 B 这条入边，但 B
可能位于互斥分支、不可达分支，或依赖同一条正在被改写的链。静态入度大于 1
不等于运行时存在可用替代路径。

建议把策略 C 保留为初筛，并增加替代路径验证：

1.  识别替代入边的来源节点。
2.  判断来源节点在改线后的图中是否仍可从本次事件入口到达。
3.  排除来源节点位于本次改线会切断的区域或依赖链中的情况。
4.  验证替代路径不依赖同一条即将被改写的边。
5.  检查替代路径是否改变必要节点的执行顺序。
6.  无法证明时拒绝该门对或整链，不以静态入度作为放行理由。

可进一步考虑使用支配关系或后支配关系，检查改线前后的必经汇合节点是否保持一致。

### 3.4 多个出口统一改指同一目标：必须检查出口语义

文档的改线规则会将 region 的出口指向下一对 G0；最后一对则指向自身
G1。该规则意图把原本互斥的剧情区域串接起来。

风险在于，一个 region 可能存在多个语义不同的出口：

``` text
             region
             /    \
          出口A  出口B
            |      |
          节点A   节点B
            |      |
          后续A   后续B
```

即使两个目标节点都有其他入边，也不能证明它们可以合并。两条路径可能分别负责设置标记、物品变化、角色状态或不同剧情后续。

改线前应检查：

-   多条出口是否最终指向同一个合法汇合点；
-   是否存在不同的必要执行节点；
-   是否有独立结果节点或状态写入；
-   是否改变原有先后顺序；
-   所有出口是否都能安全接入下一门对。

只要存在无法证明安全的不同出口，就应跳过该链组，而不是把所有出口强制合流。

### 3.5 P1 可达性：还需检查执行顺序与新增路径

文档报告原版可达剧情节点改线后仍可达，当前离线检查为 0
张图违规。这是必要条件，但不是充分条件。

例如：

``` text
原版：
剧情A → 写入标记 → 剧情B → 结果结算

改线后：
剧情A → 剧情B → 写入标记 → 结果结算
```

所有节点仍然可达，但剧情 B 可能读取尚未写入的标记。

建议补充两类验证：

**原版路径保持：**

-   关键状态写入与读取的先后关系；
-   物品增减与剧情触发的先后关系；
-   结果节点与结算节点的相对顺序；
-   必要前驱节点是否仍然先于依赖节点执行。

**新增路径检查：**

-   改线后新增可达的节点和路径；
-   是否产生绕过条件、标记或时间门的捷径；
-   是否能从不应到达的分支提前进入下游剧情；
-   是否改变事件终止和收尾顺序。

当前文档已指出 P1/P2
主要检查原版可达节点，尚未检查改线后新增的可达路径。这应保留为明确的未验证项，不能以"原版节点没有丢失"代替完整路径安全证明。

### 3.6 绿色结果节点：可达不等于已经结算

文档指出绿色结果节点依赖立即结算的流程判断或事件完成进行结算，但改线后是否仍经过正确结算点，目前没有证据。

建议对每个绿色结果节点验证：

1.  改线后仍然可达；
2.  从结果节点继续执行，能够到达合法结算点；
3.  不会因改线提前进入事件结束路径；
4.  不会延迟到下一轮事件才结算本轮结果；
5.  结果节点不会被跳过、重复执行或被错误覆盖。

当前绿色节点识别依赖 `m_Name` 白名单，文档列出 13
类。应额外统计未识别但具有相同结果语义的节点，避免白名单遗漏。

在结算点语义没有验证前，离线结果只能表述为"绿色结果节点仍可达"，不能表述为"结果完整结算"。

### 3.7 P3 不循环：当前证明范围应准确表述

文档的 P3 检查只从本对剧情节点（region
内）出发，沿被视为恒真的门检查是否回到自身；region 外的环不检查。

此外，当前将"队友条件 + 无条件"视为恒真，而"当与 NPC
交互"在玩家主动点击时也可能通过。它不一定造成自动循环，但可能使玩家操作后重新进入已经播放过的路径。

建议将现有性质准确命名为：

**"不存在由本次改线形成的、仅经过自动恒真门即可到达的局部无条件回环。"**

不要将它等同于"剧情绝不会重复播放"。

后续需要单独测试：

-   玩家主动交互是否能再次进入已播放剧情；
-   region 外的路径是否能回到本次剧情区域；
-   事件重新打开后是否会再次播放；
-   原版有界循环是否因改线变成无界循环；
-   Hold 的次数机制是否仍能阻止重复进入。

如果暂时没有运行期已播集合，P3
应作为有限范围的静态安全性质，而不是全局一次性播放保证。

### 3.8 运行时改线：需要事务化和安全提交时机

如果图在执行过程中被逐条修改，可能出现部分边已经改写、其他边尚未改写的中间状态。

建议采用事务式流程：

1.  **扫描阶段：** 完整读取原始图，生成不可变快照。
2.  **计划阶段：** 计算所有门对、region、出口、链组和改线计划。
3.  **验证阶段：** 完成冲突、容量、替代路径、环路、节点顺序和结算检查。
4.  **提交阶段：** 在确认图没有被执行读取的安全时机统一应用改线。
5.  **登记阶段：** 只有所有改线成功后，才登记对应的强制放行门。
6.  **失败阶段：** 任意步骤失败都恢复原连接，不留下部分改线或部分门表。

如果当前引擎无法提供安全提交时机，应选择不处理该图，而不是在活动中的图上逐条修改。

还需明确功能开关语义：如果关闭开关不会撤销已经完成的改线，那么 UI
和日志应说明开关只影响后续尚未处理的图；已经改线的图仍需要保持对应门级接管，否则可能出现"连接已改、门仍判假"。

## 4. 整链与放宽联动：状态必须先决策后放行

v271
的核心安全设计是：整链全部通过才展开；任一门对不通过则整链不展开，并把未展开门对加入禁止放宽表。

这项设计应保留，但要保证不存在"图尚未构建完成，普通放宽先执行"的时间窗口。

建议每张图维护以下状态：

  状态                      含义                   是否允许普通放宽
  ------------------------- ---------------------- ------------------------
  `UNSEEN`                  尚未开始扫描           否
  `BUILDING`                正在扫描和决策         否
  `DECIDED_EXPAND`          整链已批准并完成改线   仅按展开规则
  `DECIDED_KEEP_ORIGINAL`   已决定保持原版         否，受禁止放宽规则约束
  `BUILD_FAILED`            扫描、容量或验证失败   否

推荐顺序：

``` text
发现条件节点
    ↓
确认所在图完成扫描
    ↓
完成逐对判定
    ↓
完成整链决策
    ↓
完成改线提交
    ↓
登记展开门表 / 禁止放宽表
    ↓
允许继续执行条件判定
```

处于 `BUILDING` 或 `BUILD_FAILED` 的图，不能因为 `g_pair_ban`
尚未建立就落入普通条件放宽路径。

## 5. 离线验证建议

当前离线报告应继续保留，但建议把验证分为四层。

### 5.1 结构完整性

-   节点和边扫描是否完整；
-   `conditionPort` 是否唯一；
-   门对是否严格为当前在队条件；
-   partnerID 与 Negate 是否匹配；
-   是否存在超容量或未解析连接；
-   门对依赖图是否包含分叉、汇合或环路。

### 5.2 改线安全性

-   所有改线目标是否有效；
-   替代入边是否真正可达；
-   是否出现新孤岛；
-   是否破坏必要节点顺序；
-   是否产生新捷径；
-   是否改变结果结算路径；
-   是否存在新形成的无条件自动回环。

### 5.3 整链一致性

-   链组内所有门对是否统一展开或统一保持原版；
-   是否存在门表已登记但改线未完成；
-   是否存在已改线但门表缺失；
-   禁止放宽表是否覆盖所有未展开门对；
-   多个链组之间是否存在交叉改线冲突。

### 5.4 运行序列验证

对每张测试图记录：

``` text
GraphName
PairID
PartnerID
OriginalNodeSequence
ModifiedNodeSequence
OriginalEdgeList
ModifiedEdgeList
ExpandedGates
SkippedGates
ResultNodes
SettlementCheckpoints
NewlyReachableNodes
RepeatedNodes
DeadEnds
```

重点比较原版和改线后的执行序列，而不只是比较节点集合和边数量。

## 7. 推荐修改优先级

### P0：实机测试前完成

1.  将当前在队条件作为唯一可识别的门对条件，并在代码中做严格类型校验。
2.  对 `conditionPort` 多条件、扫描不完整和容量不足采取整图拒绝策略。
3.  将连通链组与可线性展开链分开；第一阶段拒绝分叉、汇合、交叉依赖和门对级环路。
4.  将策略 C 的"存在其他入边"降级为初筛，增加替代路径可达性验证。
5.  改线前检查不同出口的语义，不能默认所有出口都可以合流。
6.  确保整链决策、改线提交和放宽禁用登记之间不存在时序窗口。
7.  为运行时改线提供事务提交与失败回滚机制，或在无法保证时跳过该图。

### P1：扩大覆盖率前完成

1.  增加必要节点执行顺序检查。
2.  检查改线后新增可达路径，识别意外捷径。
3.  验证绿色结果节点的实际结算点。
4.  扩展 P3 检查，覆盖玩家交互重新进入和 region 外回路。
5.  对绿色节点白名单做遗漏检查。
6.  建立多链组之间的交叉依赖分析。

### P2：回归与维护

1.  建立原版执行序列基准。
2.  为每个跳过原因输出结构化日志。
3.  保存原始图快照、改线计划和提交结果，便于复现。
4.  对 PC 与 Android 使用同一套结构判据和测试图。
5.  每次游戏版本更新后重新生成离线统计，不沿用旧版本覆盖率。

## 8. 最终审查意见

v271 相比旧实现的关键改进------选择性 `G1→G0`
改线、整链统一决策、未展开门对禁止普通放宽------方向正确，且离线报告显示已知的下级切断和出口孤岛问题得到明显改善。

但当前离线结果尚不能证明：

-   每条被归为同一链的门对都有唯一正确的播放顺序；
-   目标存在其他入边时，替代路径在改线后必然可达；
-   多个出口合流不会改变标记、物品或结果节点的执行语义；
-   绿色结果节点一定完成结算；
-   改线不会产生新增捷径或玩家交互触发的重复路径；
-   运行时不会观察到部分提交的图。

因此，建议 v271
暂时保持"保守展开"策略：只自动处理结构简单、依赖顺序唯一、替代路径可证明、改线事务安全的链组。对无法证明安全的结构整组跳过，并保持原版行为。

**当前阶段的目标应是证明已展开的门对安全，而不是进一步提高 75.1%
的覆盖率。**

# 方案：按审查意见收敛（v273 计划）

> 对应审查意见：`docs/剧情分支展开功能审查意见与修改建议.md`
> 状态：**方案已定，待实施**
> 原则（引用审查结论）：**当前阶段的目标是证明已展开的门对安全，而不是提高覆盖率。**

## 一、审查意见的离线影响面（已逐项实测）

| 项 | 离线影响 |
|---|---|
| P0-1 只认 `HavePartnerCondition` | ✅ 已做（v272），门对总数不变（651） |

| P0-7 事务化改线 | 0（结构修正） |

**最终预期展开率：445 / 651 = 68.4%**（v271 是 75.1%，降 6.7 个百分点）

## 二、P0-2 的必要性（有实证）

**实测 `Fame-4-1` pid=10099 的 G0 门有 2 个条件：**

```
条件1: 需要伙伴
条件2: 判断角色带有Buff     ← 额外限制
```

**而 `find_pairs` 只取了第一个条件（`g_cond[gate]`）→ 强制放行整个门会绕过 Buff 限制 → 剧情在不该播的时候播。**

**全库 124 对门存在 `conditionPort > 1`。**

**实现：`conditionPort` 连接数 ≠ 1 → 整对拒绝。**

## 三、P0-3' 的关键修正（原判据会误伤目标图）

**审查建议「第一阶段只接受简单路径」。但直接对**原版图**判线性会误伤：**

```
R10049-2-1 原版链接: {0:[1,2], 1:[2,3], 2:[3], 3:[]}   ← 分叉（0 同时指向 1 和 2）
```

**这个「分叉」是**原版就有的捷径**（`10061 G1 → 10052`，跳过 10075），不是我们造成的。**

**而改线正是为了消除它：**

```
R10049-2-1 改线后链接: {0:[1], 1:[2], 2:[3], 3:[]}     ← 纯线性 ✓
R10049-0   原版: {0:[1,4], 1:[2], 2:[], 3:[0,4], 4:[1,2]}
           改线后: {3:[0], 0:[4], 4:[1], 1:[2], 2:[]}  ← 纯线性 ✓
```

**两种判据的离线对比：**

| 判据 | 展开数 |
|---|---|
| 按**原版图**判线性 | 289 (44.4%) |
| 按**改线后图**判线性 | **445 (68.4%)** |

**所以 P0-3' 的判据是：**

```
在「模拟改线后」的图上，链组内：
  每个门对的后继 ≤ 1
  每个门对的前驱 ≤ 1
  无门对级环路
不满足 → 整链拒绝 + 禁止放宽
```

**这仍然满足审查的本意（拒绝分叉/汇合/环），只是把判据放在「改线后」——因为改线是链的一部分，不能只按改线前的形状判断。**

## 四、P0-5 的必要性（代价极小）

**全库 146 对存在多出口（目标 > 1）：**

```
各目标下游有共同节点（有汇合）: 145 对  ← 放行
各目标下游无共同节点            :   1 对  ← 拒绝（M2190-1 pid=20001）
```

**实现：多出口时，检查各目标的下游可达集是否有共同节点（排除 G1）；无 → 整对拒绝。**

## 五、P0-4 策略 C 的替代路径验证

**审查意见正确：「存在其他入边」不等于「替代路径可达」。**

**实现（保守版）：**

```
对 G1 的每条出边 e = (g1 → X)：
  若 X 没有别的入边                      → 不改指（已实现）
  若 X 有别的入边，但**那些入边的来源节点**在「改线后的图」上从入口不可达
                                        → 不改指
  否则                                   → 改指 G0
```

**若某条边不能安全改指 → 该对的 G1→G0 **整对不做**（不是部分做，部分做会造成新的分叉）。**

## 六、P0-6 时序窗口

**问题：`keep_original_for` 可能在 `flat_build` 之前被调用 → 那时 `g_pair_ban` 为空 → 会放宽。**

**实现：给每张图维护状态：**

```
UNSEEN                  → 不放宽（还没扫描）
BUILDING                → 不放宽（正在扫描/决策）
DECIDED_EXPAND          → 按展开规则（条件恒真）
DECIDED_KEEP_ORIGINAL   → 不放宽
BUILD_FAILED            → 不放宽
```

**关键规则：**只有 `DECIDED_EXPAND` 允许放宽**；其余一律不放宽。**

**这替代了「`g_pair_ban` 只对未展开对生效」的隐式假设，消除了时序窗口。**

## 七、P0-7 事务化

**现有实现是「边算边改」，中途失败会留下半改线状态。**

**实现（折中，符合审查第 8 条「无法保证时跳过该图」）：**

```
阶段 1 扫描：完整读取图（已有）
阶段 2 计划：算 region / 出口 / 逐对判定 / 链分组 / 链线性 / 替代路径 → 全部只读
阶段 3 验证：容量、冲突、环路、顺序 → 任一不通过 → 整图跳过，一条边都不改
阶段 4 提交：统一改线（此时不再有判定，只有 port_set_conn_node）
阶段 5 登记：只有改线全部成功，才登记门表
阶段 6 失败：任一步失败 → 不登记门表（改线已发生的，记录下来并保持门表一致，避免「连接改了、门判假」）
```

**关键：把「所有验证」前移到任何改线之前。现有代码已经是「先判定后改线」的雏形（v271 的两阶段），需要补的是「链线性 / 替代路径」也放进阶段 2。**
